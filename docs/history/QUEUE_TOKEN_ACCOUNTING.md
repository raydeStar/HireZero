# Queue input accounting and the next Marketing flow

**Superseding design decision:** [measured OAuth queue admission](OAUTH_QUEUE_DECISION.md) distinguishes owner constraints from these strict prototype defaults. An exact native counter/hard output cap is not the only viable queue contract. The strict-path analysis below remains evidence; its earlier recommendation to wait for unavailable native APIs is superseded by the measured-mode proposal. No live activation is implied.

## What the limits mean

The ordinary queue's 4,000 input tokens cover **all provider input**: application role instructions, serialized employee context, message framing and runtime-added instructions. The 1,000 output-token allowance includes reasoning where the provider includes it in completion usage. Their sum is the unchanged 5,000-token reservation charged against the task, employee, department and company allowances. Cached input is not removed from the token allowance.

The separate native qualification did not use this admission path. It bounded serialized context to 4,000 UTF-8 **bytes** and application instructions to 1,000 **characters**, then observed native usage after completion. Those units and scopes differ. Its four native receipts reported 4,355–4,400 input tokens, 14–16 output tokens and 17,572 total tokens. They do not isolate an exact runtime overhead. No compatible native preflight counter or upstream completion-token ceiling was found in the pinned protocol. Empty file-based instruction sources do not mean zero runtime input.

Consequently, subtracting a measured offset or relabeling the application byte ceiling as a token ceiling would be incorrect. The local source and cached model metadata do not establish which runtime-added component accounts for every input token. Policy/permission instructions have not been disabled to reduce the number.

## Local correction

`CompanyInputAccounting` separates application tokens from runtime overhead and requires a counter identity. Unknown overhead blocks admission. The scheduler packs only optional history, counts the complete input, and saves its accounting with the exact packed-context and instruction digests. The existing 4,000/1,000/5,000 limits are unchanged. The native connection remains unqualified and cannot substitute observed usage for an exact counter. Future qualification receipts separately report application context/instruction byte sizes; they do not infer overhead tokens from those bytes.

Completed text work retains provider input/output usage as well as the total. A count mismatch or limit breach withholds content and holds further provider dispatch for reconciliation. Complete, consistent usage within the reservation is charged in full even when the draft is rejected or canceled. Known usage above the reservation is preserved explicitly with the reservation still held; the allowance is not increased. Missing/inconsistent usage remains unknown. Invalid text after a valid usage receipt does not discard that receipt. A missing reasoning sub-breakdown remains unknown, while output accounting includes all completion tokens. Inconsistent reported components/totals remain visible without settlement. Interrupted native turns have no verified final-usage marker: even usage queued before an interrupt response remains partial, with final total unknown and the reservation held. A confirmed ordinary completion received late can settle once without publishing content.

Owner cancellation now reaches the active adapter. Account serialization remains held while that adapter drains, with an eight-second local grace after cancellation/deadline. If termination remains unconfirmed, a persistent provider hold prevents another dispatch, including after restart. A complete late receipt can settle billing without publishing content or clearing that reconciliation hold. The hold currently requires owner-led reconciliation; no automatic clearing or replay is provided.

## Marketing assessment

The focused fake-provider workflow now follows a server-validated campaign brief through the ordinary queue, skill-specific draft instructions, a persisted usage receipt, a review-required artifact, exact owner content approval and task completion. It also exercises unknown/excessive runtime input before dispatch, counter drift, native-sized input over the bound, malformed text, missing/lost usage, owner cancellation, late billing and unconfirmed termination. An actual temporary HTTP fixture verifies that complete over-limit input usage is retained. These are fixture results, not a qualified native tokenizer or live Marketing draft.

## Next bounded live test

The smallest useful live flow is **one manually selected fictional Marketing brief → short internal draft → owner review**, in a fresh company root with one employee, short approved facts and no history/evidence beyond the reviewed packet. Use the pinned Luna runtime and the already verified process-local MXC boundary; leave automatic workers and Developer execution off. No publishing, handoff, external tools or repository access is needed for this first flow.

The existing strict profile cannot admit this native call, but waiting for unavailable hard token APIs is not the recommended product design. Normal strict defaults stay unchanged; no automatic worker is enabled and no observation is passed off as an exact count.

The measured branch is implemented and independently reviewed locally; see [the checkpoint](MEASURED_QUEUE_CHECKPOINT.md).
