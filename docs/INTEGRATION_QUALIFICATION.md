# Scoped integration qualification

This checkpoint qualifies code contracts against actual local HTTP and stdio processes. It does not qualify an installed live model runtime. Normal company-local mode still registers the unavailable adapter and no coding factory. No credentials were read or copied, and no live model requests or production repository changes were made.

## Review and implemented boundaries

The legacy TextOnlyOpenClaw path starts a gateway, reads an existing owner token/auth directory and prepares runtime configuration. The normal OpenClaw owner cell can expose global memory and records missing usage as zero. Those paths remain legacy services; company employees do not fall back to them. The legacy coding runner can use a persistent home, resumed threads and caller environment. Its original behavior is preserved for existing workflows, with a separate strict scope for company fixture execution.

ScopedCompanyText now uses the existing chat-completions HTTP path with an exact loopback endpoint/model, only admitted system/context messages, a fresh dispatch correlation, tools disabled and storage disabled. It follows no redirects, uses no proxy/cookies, starts no runtime, reads no authentication files and retries no request. Responses require the exact route, one complete assistant text answer, a receipt, complete input/output/total usage and admitted bounds. Tool responses and truncated/invalid output are withheld. Known usage can be settled while rejecting content; missing or ambiguous usage retains reservations.

CompanyDeveloperBridge now prepares a single-use execution proposal containing task/employee/attempt identity, context digest, canonical checkout, Git revision, content fingerprint, exact model route, write scope and expiry. A separate owner review approves the exact digest. Text dispatch cannot consume execution tasks. Both company text and coding use the same provider gate.

Read-only Git inspection uses an explicit executable, sanitized environment, disabled fsmonitor/hooks, no network operation and bounded file hashing. It rejects reparse paths and stale source. Owner-approved checkout claims prevent concurrent writers, including nested-directory aliases. The scope is checked again immediately before the coding process starts. Company schema version two adds execution grants transactionally without changing the version-one checksum.

The strict Codex runner starts a fresh ephemeral thread in an empty per-attempt state directory. It does not read the legacy sign-in home or inherit caller secrets, session state, project runtime configuration or environment overrides. Network and interactive permission expansion are disabled. Executable plus companion-assembly/config identities are pinned for the fake runtime. Completion is not accepted until the owned process lifecycle confirms termination; output then needs the expected route, usage and repository outcome. Unknown coding usage retains both reservations and the checkout claim. Revocation interrupts only the owned process, and late output cannot restore authority.

The fake executable exercises the same CodexRunner process and stdio parser used by the integration. It writes a fictional file only in a temporary approved Git checkout and verifies the actual thread/sandbox/model/environment envelope. Loopback HTTP fixtures test real serialization/transport, sibling-memory sentinels, route substitution, missing usage, tool calls, redirects, server errors and disconnected responses. Tests also cover pre-start refusal, changed checkout, single-use grants, interruption, retained claims and version-one migration.

The final gate passed 105 company checks, 420 Core checks, 642 Developer checks, 21 Host checks, 54 Integration checks and 44 Policy checks. All four Node frontend/hook test files and the headless desktop/mobile management flow passed. The solution and frontend builds passed with the existing SDK and locked dependencies. Fixture cleanup explicitly handles Git's read-only object files within the test-owned temporary root.

## What remains unqualified

- An installed OpenClaw version, binary identity and resolved configuration were not located/selected in the bounded known home-runtime locations or PATH. A live runtime identity cannot be inferred from the exported source.
- The proposed OpenAI text route is `gpt-6-luna`, following the source snapshot's route. The transport's synthetic tokenizer is not a live tokenizer. Exact compatible counting and a hard bound that includes billable reasoning must be proved.
- Setting tools/storage fields or sending a unique correlation does not prove the gateway honors them. Real gateway retrieval, bootstrap, compaction, tool and provider history behavior needs inspection and a controlled pilot.
- The proposed Developer route is `openai/gpt-6.1-sol` via Codex app-server, mapped to native `gpt-6.1-sol`. The installed CLI binary/version/hash must be explicitly selected. The current stdio contract reports total usage after completion but does not prove a hard upstream token/spending ceiling. Live bounded coding remains blocked until that control exists.
- Real OS filesystem/network confinement, hard-link/drive-alias identity, subprocess termination and interaction with any existing owner-account serialization need runtime qualification. Fixtures demonstrate the requested envelope and host fencing, not the actual model runtime's sandbox enforcement.

## Proposed owner approval package for a later pilot

No live pilot is approved or started by this checkpoint. Before asking to run one, identify the exact existing runtime executable/version/hash, Node version where applicable, configuration schema and loopback endpoint. Inspect only the selected runtime's code/configuration boundary, without copying credentials or changing the active OpenClaw task. Choose a free endpoint; do not reuse or stop an existing listener. The owner must establish the intended authentication separately if it is unavailable.

The first proposed pilot is text-only: OpenAI `gpt-6-luna` through that pinned OpenClaw chat-completions route, no fallback, four serial requests in a fresh company root with two fictional employees. Data consists only of fictional approved knowledge, short employee-specific sentinel notes, their own test conversation history and selected fictional evidence. No real project files, personal notes, employer data or global memory may enter a request. Inspect the actual resolved request/runtime traces as well as the answers.

Proposed ceiling: four requests, each at most 4,000 input and 1,000 completion tokens including any billable reasoning, no retry and a 60-second local deadline. Reserve at most 20,000 tokens in aggregate; uncertain usage remains reserved and stops the pilot for reconciliation. The route must prove those bounds before execution. No monetary spending is authorized here: disclose the selected account/plan and any applicable credit cost, then obtain an explicit monetary cap if the route can charge credits. Abort if a hard bound or complete usage is unavailable.

Permissions for that text pilot are limited to the fresh local data root and the exact loopback gateway endpoint. There are no tools, shell commands, repository writes, network retrieval, credential changes, publication, deployment or production migration. Validate employee isolation, no ambient retrieval/history/tools, exact routing, complete usage, cancellation/unknown outcomes and serialized account access. Failure leaves live execution disabled.

A Developer pilot requires separate approval after the text boundary and spending control are qualified. Limit it to one fictional temporary Git repository, one exact approved task and fresh ephemeral thread, no network, no credentials, no MCP/plugins, no commits/pushes and no production checkout. Review the exact file scope and repository fingerprint first. A verified hard usage ceiling is a prerequisite; the current post-hoc total alone is insufficient to approve live execution.
