## CPU-only protocol repair, 2026-10-15

The refused payload contains `sandboxPolicy.access.type="restricted"`. This is a confirmed serialization incompatibility in the exact installed `0.162.0-alpha.17.2` release, rather than an unspecified schema gap. Its custom `SandboxPolicy` deserializer explicitly rejects the legacy restricted-read field. The corresponding public unit test uses the same field shape. Both rejection literals are present in the pinned executable. The generated JSON Schema permits unknown properties and therefore accepts the old payload; schema validation alone would miss this error.

The matching release maps deserialization errors to JSON-RPC `-32600`, with the fixed diagnostic `readOnly.access is no longer supported; use permissionProfile for restricted reads`. Its stdio processor deserializes the request before dispatch or turn admission. Consequently this exact payload cannot start a remote turn through that parser. This is source-based evidence about the submitted request, not a recovered error or billing receipt: the original client discarded its response code/message, and no turn ID or usage receipt was retained. Do not reinterpret absent usage or unchanged balances as an invoice proving zero account activity.

The repair configures a process-local named permissions profile: a single read rule for that attempt's empty scratch directory, no inherited profile or workspace roots, and network disabled. It selects `permissions="hirezero_qualification"` on both thread and turn requests, omitting `sandbox`, `sandboxPolicy` and the obsolete inline `permissionProfile` parameter. Despite the older rejection literal's wording, the supported request field is `permissions` containing a profile name. The connector checks effective configuration and profile availability before thread creation, then verifies returned profile provenance, exact route, zero instruction sources, ephemeral state, read-only/no-network compatibility policy and `approvalPolicy="never"`. It never relaxes the profile to full filesystem reads.

Minimal corrected turn parameters, after the isolated thread and named profile are verified:

```json
{"threadId":"fictional-thread","model":"gpt-6-luna","effort":"low","summary":"none","approvalPolicy":"never","permissions":"hirezero_qualification","environments":[],"runtimeWorkspaceRoots":[],"serviceTierForTurn":"default","input":[{"type":"text","text":"Fictional employee context"}]}
```

CPU validation used only `initialize`, `config/read` and `permissionProfile/list` in a fresh unauthenticated home. The installed native server accepted the process-local profile and reported it allowed. Corrected thread/turn examples pass the installed generated schemas; the legacy example also passes, demonstrating the custom-deserializer limitation. Stdio fixtures now reject the old field before synthetic turn admission, reject mixed permission mechanisms, broader reads, inherited profiles, network access, disallowed profiles and wrong provenance. Diagnostics preserve the numeric code and exact allowlisted public messages; unknown messages, appended private text and error data remain withheld. Every refusal still closes the connection without replay. Validation: 156 deterministic company checks pass; affected projects compile.

No native `turn/start`, inference, login or account change occurred during this repair. Actual Windows enforcement of the restricted profile and successful live turn compatibility remained unqualified at this checkpoint. Luna routine/Sol coding routing, employee context boundaries, credit reservations and disabled automatic workers remain unchanged. Owner approval for recoverable same-scope continuation was subsequently confirmed; the Windows enforcement result above supersedes the earlier pause pending an owner decision. Uncertain admitted outcomes are still never automatically replayed.

Matching public release evidence: [custom deserializer](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server-protocol/src/protocol/v2/permissions.rs#L607), [regression test](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server-protocol/src/protocol/v2/tests.rs#L2916), [deserialization before dispatch](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server/src/message_processor.rs#L662), [error code](https://github.com/openai/codex/blob/740e5af33c71225640e0c1c1555c514c2c93ab74/codex-rs/app-server/src/error_code.rs#L14). ## What remains unqualified

- The proposed OpenAI text route is `gpt-6-luna`, following the source snapshot's route. The transport's synthetic tokenizer is not a live tokenizer. Exact compatible counting and a hard bound that includes billable reasoning must be proved.
- Setting tools/storage fields or sending a unique correlation does not prove the gateway honors them. Real gateway retrieval, bootstrap, compaction, tool and provider history behavior needs inspection and a controlled pilot.
- The proposed Developer route is `openai/gpt-6.1-sol` via Codex app-server, mapped to native `gpt-6.1-sol`. The installed CLI binary/version/hash must be explicitly selected. The current stdio contract reports total usage after completion but does not prove a hard upstream token/spending ceiling. Live bounded coding remains blocked until that control exists.
- Real OS filesystem/network confinement, hard-link/drive-alias identity, subprocess termination and interaction with any existing owner-account serialization need runtime qualification. Fixtures demonstrate the requested envelope and host fencing, not the actual model runtime's sandbox enforcement.
