# ADR 0147: Useful specialist starter plans and direct review

Status: implemented and installed; fictional journeys and one fresh native evaluation per role complete.

## Context

The installed CEO and Developer starters ran successfully through the high-effort Codex path. Both respected
their boundaries, but their first tasks largely asked the owner to create another plan or specification. That
defers the useful artifact and repeats the generic-first-result problem already addressed for Marketing.

The same walkthrough exposed misleading handoff states: an ordinary pending save briefly claimed its outcome
needed recovery, the hiring guide opened a work list instead of the exact saved request, and a recovered read
failure left a stale global error visible through later successful work.

## Decision

- Keep each role's instructions and setup request in its own module. CEO starter plans rank priorities, explain
  sequencing and deferral, estimate timeboxes, and include a usable first-task brief plus any small template or
  question it needs. Developer starters compare a manual/no-build option and supply a small spec or template,
  a fictional completed example, observable checks and minimum evidence needed before implementation.
- Keep these as private advice. Missing technical access is not invented or granted; cited facts, hypotheses,
  estimates and fictional examples remain distinct. Explicit owner requirements still govern the task. No new
  model, effort, allowance, execution permission or automatic repair loop is introduced.
- First-assignment preparation and recovery open the exact saved task in focused Work review. Ordinary private
  chat navigation remains available. While an attempt is live, show progress; only a settled unconfirmed save
  shows recovery instructions. Persist its operation identity and never replay an uncertain save.
- Track workspace/conversation read failures separately from command failures. Successful current reads clear
  only their own notice; stale responses cannot replace newer read state. A failed command remains visible
  until dismissed or a later explicit command, even when background polling succeeds. Refreshing the workspace
  never submits work and preserves unfinished forms.

## Verification boundary

The fictional first-result journey verifies pending progress, lost-reply reconciliation, exact task navigation,
read recovery with draft preservation, and command-error retention after successful polling. The guided-hiring
journey covers desktop/mobile setup and definitive/uncertain outcomes. Native evaluations use fresh private
threads and the current approved brief without seeding earlier deliverables; they assess individual outputs,
not consistent model quality or customer acceptance. Existing Marketing instructions and approved recurring
authority are unchanged. See [evaluation and delivery evidence](../history/2026-10-27-specialist-first-work.md).

The fresh Developer output contains a usable no-build template and fictional filled example. The fresh CEO
output contains sequenced priorities, timeboxes, a deferral and a first-task brief with a question/example,
but omits the requested brief-field citations. A separate, visibly identified assistant editorial copy adds
only those references; the native original is preserved. These samples do not establish repeatable adherence
or owner usefulness acceptance. No further model request was used for that deterministic correction.
